# 微信小程序虚拟支付全量接入设计

## 目标

将小程序内所有虚拟商品购买从普通微信 JSAPI 支付迁移到微信官方“小程序虚拟支付”，覆盖 iOS、Android 等终端。首批商品包括 Plus、Pro 和点数补充；以后新增的会员、点数、数字内容或功能权益也必须通过同一虚拟商品目录接入。

网页扫码支付和实体商品支付不在本次迁移范围内，继续使用现有普通微信支付能力。

## 当前状态

- 小程序 `pages/pro` 通过 `/api/billing/orders` 创建订单。
- 后端通过微信支付 v3 JSAPI 下单，返回 `wx.requestPayment` 参数。
- 普通微信支付通知将订单标记为已支付，并发放会员和点数权益。
- 网页端使用普通微信 Native 扫码支付。

当前小程序链路将虚拟会员和点数作为普通微信支付商品处理，不满足新的虚拟商品支付要求。

## 外部前置条件

上线前必须在微信小程序后台完成：

1. 开通“小程序虚拟支付”能力并通过准入审核。
2. 取得正式环境 Offer ID、支付应用密钥等官方要求的配置。
3. 在道具管理中录入与本系统虚拟商品目录对应的商品，并启用发货通知。
4. 配置支付、发货、退款和投诉相关的消息推送。
5. 准备独立的沙箱参数进行联调。

密钥和正式环境参数只允许通过环境变量或服务器密钥文件注入，不写入仓库。

## 方案选择

采用独立虚拟支付适配层。普通微信支付和虚拟支付共享本地账单与权益发放能力，但不共享签名、客户端调起、通知解析或退款实现。

不在现有普通微信支付函数中堆叠虚拟支付分支，因为两种能力的协议、签名、回调和退款语义不同。也不替换网页扫码支付或未来实体商品支付。

## 领域模型

### 虚拟商品目录

服务端维护白名单商品目录，每个商品至少包含：

- 稳定的 `productId`，与微信后台道具配置一致。
- 对应的内部套餐或点数权益。
- 服务端价格、币种和展示名称。
- 发放策略和退款回收策略。
- 是否启用及允许的购买数量。

客户端只提交 `productId` 和允许的购买数量。价格、权益、Offer ID、环境及订单号均由服务端确定，禁止客户端覆盖。

首批目录映射：

- Plus 会员商品。
- Pro 会员商品。
- 点数补充商品；若当前产品尚无独立点数 SKU，则先复用现有“会员有效时购买套餐补点”的业务语义，并在实现计划中以当前套餐数据为准，不凭空新增面额。

### 支付订单

沿用 `PaymentOrder` 作为本地账单主记录，增加能够明确区分普通微信支付与微信虚拟支付的通道字段，以及虚拟商品 ID、购买数量、官方环境和必要的官方交易标识。

历史订单保持可读，不迁移或重写已有普通微信支付记录。新虚拟订单必须能由 `outTradeNo` 唯一定位，并支持重复通知幂等处理。

## 接口和数据流

### 创建订单

小程序调用新的虚拟订单接口：

`POST /api/billing/virtual-orders`

请求只包含商品 ID、允许的数量和本次 `wx.login` 的一次性 code。服务端完成以下操作：

1. 校验登录用户和商品目录。
2. 从服务端目录读取价格和权益。
3. 创建本地待支付订单。
4. 使用客户端本次 `wx.login` 的一次性 code 调用 `auth.code2Session`，取得当前有效 `session_key`。
5. 按官方协议生成完全一致的 `signData`。
6. 使用 AppKey 计算 `paySig`，使用当前 `session_key` 计算 `signature`。
7. 返回 `wx.requestVirtualPayment` 所需的最小参数集。

签名原串必须直接返回并原样传给微信客户端 API，客户端不得重新序列化或改写字段顺序和内容。`session_key` 只在服务端本次请求内使用，不持久化、不写日志，也不返回客户端；openid 不能替代 `session_key`。

### 客户端支付

`pages/pro` 对虚拟商品只调用 `wx.requestVirtualPayment`。客户端成功回调仅表示微信客户端流程完成，页面进入“正在确认权益”状态，不直接发放会员或点数。

客户端随后轮询现有或新的订单查询接口，直到服务端订单进入终态；取消、失败和超时显示明确提示，并允许用户重新查询未完成订单。

不再为小程序虚拟商品回退到 `wx.requestPayment`。开发环境可使用显式 mock 或官方沙箱，但不得因缺少虚拟支付配置而静默调用普通支付。

### 服务端通知和发货

新增独立虚拟支付通知入口，按官方定义分别解析商品发货、代币支付、退款和投诉事件。由于当前官方文档没有定义可用于该 HTTP 推送的通用验签头、规范串或防重放算法，通知只作为“需要核单”的触发信号，不能直接发放或回收权益。处理顺序为：

1. 保留通知原始请求体。
2. 按官方 Event 名称解析为判别联合类型，不为不同事件虚构共同字段。
3. 用通知中的商户订单号定位本地订单，但不因此改变订单或权益。
4. 使用通知中的 openid 仅作为微信官方查单的查询选择器，与本地订单号一起调用 `/xpay/query_order`；该 openid 不作为发货证据。
5. 使用可信查询结果校验 Offer ID、环境、商品、订单号、openid 和金额。
6. 使用官方交易 ID 与本地订单状态幂等更新订单并发放或回收权益。
7. 投诉事件只记录最少必要信息并告警，不改变订单或权益。
8. 返回官方要求的确认响应。

可信的官方查单结果是权益到账的最终依据。通知和客户端成功回调都只能触发核单，不能替代查单。漏通知时由客户端轮询或补偿任务触发查单恢复订单。

### 退款和投诉

虚拟支付订单不调用现有普通微信支付 v3 退款接口。退款申请、状态查询和退款通知全部进入虚拟支付适配层；退款完成后继续复用当前“按剩余点数折算并回收权益”的业务规则，但具体可退金额必须同时满足微信虚拟支付规则。

投诉通知只记录和告警，不自动退款或改变用户权益，除非后续有明确产品规则。

## 组件边界

- `backend/src/services/virtualPaymentProducts.ts`：商品白名单、价格和权益映射。
- `backend/src/services/wechatVirtualPayment.ts`：`code2Session`、官方参数构造、签名、查单、退款和按事件区分的通知解析。
- `backend/src/routes/billing.ts` 或独立 billing 子路由：鉴权、订单所有权和 HTTP 响应；不在路由中实现密码学。
- `backend/src/services/billing.ts`：继续拥有本地订单和会员/点数发放规则。
- `apps/wechat-miniprogram/pages/pro/index.js`：选择商品、调用后端、拉起 `wx.requestVirtualPayment`、轮询服务端结果。

如果实现时官方接口要求的边界与上述文件划分不同，可以调整文件名，但普通支付与虚拟支付协议必须保持隔离。

## 配置

至少需要独立表达以下配置概念，确切环境变量名在实施计划中结合现有命名确定：

- 虚拟支付是否启用。
- 沙箱或正式环境。
- Offer ID。
- 支付签名密钥及其安全存储位置。
- 官方回调验证配置。
- 各虚拟商品的微信后台商品 ID。

服务启动时应校验启用环境所需配置。生产环境缺少配置时拒绝创建虚拟订单；本地测试只有显式开启 mock 时才允许模拟支付。

## 错误处理

- 未开通或配置不完整：返回可识别的服务端错误，不回退普通支付。
- 商品不存在、停售或价格不匹配：拒绝下单。
- 用户取消：订单保持待支付或按官方状态关闭，不显示支付成功。
- 客户端成功但通知延迟：显示等待确认并持续查单。
- 重复通知：返回成功但不重复发权益。
- code 换取 session 失败、查单失败或可信订单字段不匹配：拒绝发货并记录安全日志。
- 发货过程中断：允许同一通知或补偿任务安全重试。

日志不得记录支付密钥、完整签名材料或用户敏感信息。

## 测试与验证

实施使用测试先行，至少覆盖：

1. 服务端商品目录不接受客户端价格覆盖。
2. `signData` 字符串与签名输入完全一致。
3. 通知只触发查单，不直接发放权益。
4. 可信查单成功后发放权益，重复通知/查单不重复发会员或点数。
5. 金额、商品、Offer ID、环境或订单用户不匹配时拒绝发货。
6. 退款通知按现有规则回收权益且保持幂等。
7. 小程序只对虚拟商品调用 `wx.requestVirtualPayment`。
8. 小程序不再回退 `wx.requestPayment`。
9. 客户端成功后等待服务端终态。
10. 普通网页扫码支付测试保持通过。

本地自动化通过后，还必须在微信开发者工具和官方沙箱中验证完整的“下单、支付、通知、到账、退款”链路。正式环境真实支付、生产回调配置、服务器密钥安装、上传和发布均需单独明确授权。

## 迁移顺序

1. 建立商品目录、订单字段和虚拟支付服务端适配层。
2. 接入通知、查单和幂等权益发放。
3. 将小程序 Pro 页面切换到虚拟支付并完成沙箱验证。
4. 为旧小程序版本保留短期普通订单查询能力，但新版本不再创建普通 JSAPI 虚拟订单。
5. 沙箱闭环通过后，再配置正式商品和回调并发布。

## 不在本次范围

- 生产环境配置、部署和小程序上传发布。
- 网页扫码支付改造。
- 实体商品支付改造。
- 新增未经产品确认的会员档位或点数面额。
- 自动处理投诉或改变现有退款业务规则。

## 完成标准

- 所有小程序虚拟商品通过 `wx.requestVirtualPayment` 下单。
- 服务端使用当前 `session_key` 完成签名，并通过通知触发的可信查单实现幂等发货。
- Plus、Pro 和现有点数补充语义均由统一商品目录驱动。
- 普通微信支付不再承载小程序虚拟商品，但网页和实体商品链路不受影响。
- 自动化测试通过，且官方沙箱完成端到端验证后才具备上线条件。
