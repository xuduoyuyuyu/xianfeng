# 未登录状态直接进入登录流程设计

## 背景

当前 Web 已有统一登录弹窗，小程序 WebView 已能回到原生手机号登录，但原生小程序的部分页面在接口返回 `401` 后仍直接展示“未登录或登录已过期”。用户看到的是错误文案，而不是可立即完成的登录流程。

## 目标

- 受保护接口或操作确认用户未登录时，直接调起当前端已有的登录能力。
- 登录成功后回到原页面并重新加载原受保护数据。
- 不再把“未登录或登录已过期”作为页面错误文案展示。
- 公开页面和公开数据仍可匿名浏览，不因没有本地 token 而统一变成登录墙。

## 方案选择

采用“认证失败触发、各端复用现有登录入口”的方案：

- Web 继续通过全局 `xf-show-login-modal` 打开登录弹窗。
- 小程序 WebView 继续通过现有桥接进入原生手机号登录覆盖层。
- 原生小程序在请求返回 `401` 时发出统一的登录请求，由当前页面显示已有风格的手机号登录覆盖层；登录成功后关闭覆盖层并重新执行页面加载。

不新建第二套账号系统或独立登录页，也不在所有公开页面首次进入时强制登录。这样既覆盖真实认证失效，又不会破坏公开内容浏览。

## 组件与职责

### 原生小程序请求层

`utils/request.js` 继续负责识别 `401` 和清理失效会话，并新增一个轻量的认证失效通知。通知只传递“需要登录”这一事实，不负责页面跳转、展示文案或重试业务请求。

同一批并发 `401` 必须合并，避免重复打开多个登录层。

### 原生小程序页面层

会发起受保护请求的页面订阅认证失效通知，并复用已有 `open-type="getPhoneNumber"` 登录能力显示全屏登录覆盖层。登录成功后：

1. 保存新的登录态；
2. 关闭登录覆盖层；
3. 重新执行该页面原有的加载函数；
4. 不保留此前的认证错误文案。

本轮首先覆盖已复现问题的福利页，并把通知与登录处理做成可复用边界，供其他原生页面接入；已有 Xiaowanzi 和 WebView 登录覆盖层保持原行为。

### Web 与小程序 WebView

保留 `frontend/src/services/api.ts` 的统一 `401` 路由。页面自己的 `catch` 不再用认证错误覆盖登录界面；非认证错误仍按原逻辑展示。

## 数据流

1. 页面请求受保护接口。
2. 服务端返回 `401`。
3. 请求层清理失效 token，并触发一次登录请求。
4. 当前端打开登录界面，业务页不显示认证错误文案。
5. 用户完成手机号登录。
6. 登录界面关闭，页面重新加载原数据。
7. 若用户拒绝授权，登录界面保留并允许再次操作，不伪造业务成功状态。

## 错误处理

- `401`：调起登录，不展示后端认证文案。
- 非 `401`：保留现有友好错误处理。
- 用户拒绝手机号授权：显示登录组件自身的明确提示，不回落为“登录已过期”。
- 登录接口失败：保持登录层可见，并展示登录失败原因。
- 并发 `401`：只触发一次登录请求。

## 验证标准

- 原生福利页在无效或过期登录态下不再显示“未登录或登录已过期”，而是显示手机号登录入口。
- 完成登录后，福利页重新请求数据并恢复正常内容。
- 用户拒绝授权后仍停留在登录入口，可再次尝试。
- Web 普通页面的 `401` 仍打开登录弹窗；小程序 WebView 的 `401` 仍进入原生登录覆盖层。
- 匿名访问公开接口和公开页面不被主动拦截。
- 并发 `401` 不产生重复登录层或重复导航。

## 不在本次范围

- 修改后端 `401` 文案。
- 强制所有公开页面首次进入即登录。
- 新建独立账号密码登录页。
- 自动重放可能产生副作用的写操作；登录成功后只重新加载页面数据，用户需重新确认写操作。
